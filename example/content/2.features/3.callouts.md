# Callouts

Use this page to learn the semantic **tones** and visual **variants** of the SDS Lite callout component.

## What are callouts?

Callouts are styled message blocks used to surface supporting information directly within content. They are useful for notes, warnings, tips, and success messages that should stand out from body text.

## Why use callouts?

Callouts help:

- **Highlight priority guidance** without interrupting the main flow.
- **Improve scanability** by making key notes easy to spot.
- **Keep meaning consistent** with reusable tone and variant conventions.

## Configuration Options

### Variant
Defines the **level of visual emphasis**.

- **`bold`** — Use when the message is critical or requires high visual emphasis.  
- **Omit `variant`** — Use the default subtle surface for secondary messages.  
- **`outline`** — Use for minimal emphasis, often for inline tips or supporting info.  

### Tone
Determines the **color meaning** or semantic purpose.

- **`info`** — Tips, help messages, or general information.  
- **`success`** — Success, confirmation, or positive outcomes.  
- **`warning`** — Warnings, cautions, or potential issues.  
- **`danger`** — Errors, failures, or critical blocking problems.  
- **`neutral`** — Neutral, supporting, or reference info; the default.  
- **`accent`** — Highlights or announcements.  

### Size
Controls the **padding and visual density** of the callout.

- **`sm`** — Smaller padding and font size; best for compact layouts.
- **`md`** — Default size; balanced spacing for general use.  
- **`xs`** and **`lg`** — Extra compact or prominent guidance.

## Markdown Format

::code-block
```markdown
::callout{variant="outline" tone="info" size="sm"}
**Info:** Use this format to provide context or definitions that help clarify a topic without interrupting the main flow.
::
```
::



## Info - Informational notes

Use the **info** tone to share background context, helpful hints, or additional explanations that aid reader understanding.  

### Outline

::callout{tone="info" variant="outline" size="sm"}
🌟 **Info:** Use this format to provide context or definitions that help clarify a topic without interrupting the main flow.
::

### Subtle

::callout{tone="info"}
💡 **Tip:** When referencing internal systems, always include the full acronym on first mention to help new readers understand.
::

### Bold

::callout{tone="info" variant="bold"}
🕚 **Note:** This section is periodically updated as the design system evolves. Check the version history for recent changes.
::

## Success - Positive information

Use the **success** tone for highlighting helpful outcomes, confirming good practices, or reinforcing recommended approaches.  
It draws attention to “what works well” or validated methods.

### Outline

::callout{tone="success" variant="outline"}
🌿 **Tip:** Consider documenting examples from real projects to help illustrate how a component is used successfully.
::

### Subtle

::callout{tone="success"}
✅ **Good Practice:** Keep each documentation page focused on one concept or component to make information easier to find.
::

### Bold

::callout{tone="success" variant="bold"}
🏆 **Recommended:** Teams that standardize on shared documentation templates reduce onboarding time by up to 40%.
::

## Warning - Cautions

Use the **warning** tone to highlight potential confusion, common mistakes, or critical editorial cautions.  
It helps readers avoid misinterpreting or misusing the information.

### Outline

::callout{tone="warning" variant="outline"}
⚡ **Heads-up:** Some diagrams or screenshots may depict earlier versions of the interface. Always confirm component styles against the current release.
::

### Subtle

::callout{tone="warning"}
⚠️ **Caution:** Avoid duplicating design tokens in code samples. Reference them directly from the shared design system package.
::

### Bold

::callout{tone="warning" variant="bold"}
🚧 **Important:** Deprecated components should not be documented as “current.” Move them to the Legacy section to prevent confusion.
::

---

## Danger - Critical information

Use the **danger** tone for major documentation issues or content that requires immediate attention.  
It should be used sparingly and only for serious errors or blockers.

### Outline

::callout{tone="danger" variant="outline"}
🧯 **Reminder:** Remove placeholder text and dummy data before publishing any public-facing documentation.
::

### Subtle

::callout{tone="danger"}
❗ **Attention:** This page references an outdated API endpoint. Verify that all examples align with the current API version.
::

### Bold

::callout{tone="danger" variant="bold"}
🚫 **Critical:** Do not publish this page until the referenced security guidance has been reviewed and approved.
::

## Neutral - Supporting information

Use the **neutral** tone for neutral, contextual, or supporting material that complements the main content.  
It’s ideal for side notes, references, or meta information.

### Subtle
